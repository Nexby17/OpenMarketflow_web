## 1. ОБЩИЕ ТРЕБОВАНИЯ

### 1.1 Назначение
Разработка арбитражной стратегии и торгового робота для выявления и использования ценовых неэффективностей между парами финансовых инструментов на бирже MOEX через брокера Финам.

### 1.2 Целевые показатели (реалистичные)

| Параметр             | Минимум | Цель       | Комментарий                              |
|----------------------|---------|------------|-------------------------------------------|
| Доходность годовых   | 12%     | 18-24%     | После комиссий и проскальзывания          |
| Макс. просадка       | < 15%   | < 10%      | Включая комиссии и slippage              |
| Sharpe Ratio         | ≥ 1.0   | ≥ 1.3      | На дневных returns                        |
| Win Rate             | ≥ 55%   | 60%+       | Сделки с положительным PnL               |
| Profit Factor        | ≥ 1.5   | ≥ 1.8      | Gross profit / gross loss                 |
| Avg Slippage (маркет)| < 0.08% | < 0.05%    | На агрессивной ноге                       |
| Fill Rate (лимитка)  | ≥ 70%   | ≥ 85%      | IOC исполнение                            |

> **Почему не 20% Sharpe:** На Финаме с рыночным исполнением, 150-300мс latency и 3-5 б.п. slippage — Sharpe ≥ 2.0 недостижим без co-location и HFT инфраструктуры.

### 1.3 Поддерживаемые типы пар

| Тип                     | Пример              | Комментарий                           |
|-------------------------|---------------------|---------------------------------------|
| Спот / Фьючерс         | SBER / SBRF-U6      | Базисный арбитраж                     |
| Фьючерс / Фьючерс      | SiU6 / SiM6         | Календарный спред                     |
| Фьючерс / Индекс       | MIXU6 / SiU6        | Парный трейдинг (кросс-инструментный) |

> **Спот/Спот (ROSN/SBER) убран:** Акции разных секторов (нефть vs финансы) не коинтегрированы. Коинтеграция проверяется на Этапе 0. Если ADF тест проходит — можно добавить.

### 1.4 Архитектура

- **Брокер:** Финам (gRPC для ордеров, REST для свечей, SubscribeQuote для стакана)
- **Размещение:** Вкладка «Арбитраж» в TradesFINAM (аналог Order Flow)
- **Язык:** Python (один модуль, аналогично OF-роботу)
- **Данные:** API Финам + MOEX ISS (для дивидендов/спецификаций)
- **Хранение:** JSON state + CSV trade log (аналог OF: `arb_state.json`, `arb_trades.csv`)
- **Логирование:** Structured JSON в systemd journal (аналог OF-робота)

## 2. ЭТАПЫ РАЗРАБОТКИ

### Этап 0: Валидация пар (3-5 дней, ДО кода стратегии)

**Цель:** Доказать, что выбранные пары имеют арбитражный edge.

**Действия:**
1. Скачивание 2 лет дневных/часовых данных по каждой паре (MOEX ISS / Finam)
2. ADF-тест (Augmented Dickey-Fuller) — проверка стационарности спреда
3. Johansen test — проверка коинтеграции, получение eigenvector для hedge ratio
4. Расчёт rolling Z-score на исторических данных
5. Оценка гипотетического PnL: входят при Z > 2, выходят при Z < 0.5
6. Расчёт комиссий и slippage на основе реальных данных (OF-база для Si)

**Критерий прохождения:**
- ADF p-value < 0.05 (спред стационарен)
- Johansen trace statistic > critical value at 5%
- Гипотетический PnL после комиссий > 0 за 2 года
- Rolling correlation > 0.7 в 80%+ окон

**Результат этапа:** Список валидированных пар с рассчитанными hedge ratio, окном Z-score и ожидаемыми метриками.

### Этап 1: Бэктест-движок (1 неделя)

**Вход:** Результаты Этапа 0 (валидированные пары, hedge ratio)

**Действия:**
1. Загрузка 2 лет минутных данных (Finam API)
2. Расчёт spread и Z-score с рассчитанным hedge ratio (Johansen eigenvector)
3. Модель исполнения: пассивно-агрессивная (лимитка + маркет)
4. Модель издержек: точные комиссии Финам + slippage (3-5 б.п. на маркет) + задержка (150-300 мс)
5. Walk-Forward: обучение 6 мес → тест 3 мес → сдвиг → повтор
6. Отчёт: equity curve, trade log, Sharpe, DD, PF, regime analysis

**Критерий:** Стратегия прибыльна на out-of-sample (последние 6 мес) с учётом всех издержек.

**Если бэктест убыточен →** ТЗ останавливается, пары или параметры пересматриваются.

### Этап 2: Ядро стратегии + Исполнение (2-3 недели)

1. Spread Calculator (Z-score, fair value, adaptive window)
2. Signal Generator (вход/выход по порогам)
3. Order Manager (пассивно-агрессивная модель, IOC + FOK, retry)
4. Risk Controller (лимиты, стопы, kill-switch)
5. Roll Manager (роллирование календарных спредов)
6. Reconciliation (сверка с Finam GET /positions)

### Этап 3: Paper Trading (2-4 недели)

1. Полная эмуляция с учётом задержек
2. Мониторинг: fill rate, slippage, latency, correlation drift
3. Корректировка параметров на основе paper results
4. При Paper PnL > 0 за 2 недели → переход на прод (минимальный объём)

### Этап 4: UI (1-2 недели)

1. Вкладка «Арбитраж» в TradesFINAM
2. Панель пар + параметры + графики + лог

## 3. ЛОГИКА СТРАТЕГИИ

### 3.1 Основной алгоритм

| #  | Этап             | Условие / Триггер                                    | Действие                                                        | Результат                  |
|----|------------------|------------------------------------------------------|-----------------------------------------------------------------|----------------------------|
| 1  | Мониторинг        | Непрерывно (каждый бар / каждые N сек)              | Spread = Price_A - HedgeRatio × Price_B                        | Текущее значение спреда    |
| 2  | Z-score           | Каждый расчётный тик                                | Z = (Spread - Mean) / Std на скользящем окне LookbackWindow    | Стандартиз. отклонение     |
| 3  | Фильтр волатильн. | Перед входом                                         | ATR(14) / Price < MaxATRPct И Liquidity > MinLiquidityVolume   | Допуск к торговле          |
| 4  | Фильтр корреляции | Перед входом (ежечасно)                              | Rolling correlation > MinCorrelation (0.7)                     | Пара ещё коинтегрирована   |
| 5  | Фильтр событий    | Перед входом                                         | Нет макро-событий (ЦБ заседания ±1 день), нет дивидендной отсечки | Безопасное окно           |
| 6  | Сигнал входа      | Z > EntryZ                                           | Пассивно-агрессивное исполнение (Раздел 5)                      | Обе ноги исполнены         |
| 7  | Мониторинг        | Непрерывно                                           | PnL, hold time, Z-score                                         | Текущий статус             |
| 8  | Выход: целевой    | Z < ExitZ И PnL > 0                                 | Закрытие обеих ног                                              | Прибыль зафиксирована      |
| 9  | Выход: тайм-стоп  | HoldTime > MaxHoldMinutes                           | Принудительное закрытие                                         | Капитал освобождён         |
| 10 | Выход: катастрофа | Z > EmergencyZ ИЛИ PnL < StopLossRub               | Немедленное закрытие, алерт                                      | Убыток ограничен           |
| 11 | Ребалансировка    | Каждые RebalanceDays ИЛИ corr < MinCorrelation       | Пересчёт hedge ratio через Johansen (на накопленных данных)     | Актуальный хедж            |
| 12 | Роллирование      | DaysToExpiry ≤ RollWindowDays (только фьюч/фьюч)    | Закрытие Near/Far, открытие Far/NextFar                         | Позиция перенесена         |

### 3.2 Обработка ошибок входа

| Сценарий                            | Условие                              | Действие                                                |
|--------------------------------------|---------------------------------------|---------------------------------------------------------|
| Лимитка (нога А) не исполнилась      | LegATimeoutSec истёк                 | Отмена заявки, сигнал отменён, лог                      |
| Частичный fill < 50%                 | FillQty / OrderQty < MinFillRatio    | Отмена остатка, сигнал отменён                            |
| Частичный fill ≥ 50%                 | FillQty / OrderQty ≥ MinFillRatio    | Объём ноги Б = FillQty × HedgeRatio, маркет              |
| Маркет (нога Б) не исполнилась       | Ошибка API / клиринг                 | Экстренное закрытие ноги А по рынку, алерт              |
| Задержка > MaxLegDelayMs            | T_B - T_A > MaxLegDelayMs            | Сделка состоялась, пометка «sync_violation» в логе      |
| Slippage > MaxSlippageBps            | ExecPrice - SignalPrice > threshold   | Отмена, повтор с коррекцией или отказ                   |
| Рассинхрон стейта                    | Local positions ≠ Broker positions   | Алерт, auto-reconciliation, блокировка входа            |
| Сбой подключения                     | Timeout / ошибка API                 | Exponential backoff, circuit breaker при 3+ ошибках    |
| Rate limit (Финам)                    | > 15 orders/sec                      | Queue + throttle, лог «rate_limited»                    |
| Stakan опустел                       | TotalVolume < MinLiquidityVolume    | Отмена лимитки, блокировка на CooldownSec               |

### 3.3 Логика роллирования (календарные спреды)

| Параметр             | Значение          | Комментарий                              |
|----------------------|-------------------|------------------------------------------|
| Окно роллирования    | 10-15 дней до экспирации | Настраиваемый (RollWindowDays)    |
| Триггер              | DaysToExpiry ≤ RollWindowDays | Проверка каждый день          |
| Действие             | Закрыть Near/Far, открыть Far/NextFar | Синхронное исполнение      |
| Фильтр ликвидности   | Volume_NextFar > MinLiquidityVolume | Не роллировать в неликвид   |
| Оптимизация момента  | Минимальный спред между контрактами    | Снижение издержек переноса   |

## 4. HEDGE RATIO: МЕТОДОЛОГИЯ

### 4.1 Почему не OLS
Обычная линейная регрессия (OLS) `Price_A = α + β × Price_B` даёт смещённый коэффициент, потому что не учитывает, что оба ряда noisy. Для коинтегрированных пар нужен метод, учитывающий шум в обоих рядах.

### 4.2 Метод: Johansen Eigenvector (основной)

1. Используется Johansen test для определения вектора коинтеграции
2. Eigenvector с наибольшим eigenvalue → веса (w_A, w_B)
3. HedgeRatio = w_B / w_A (соответственно)
4. Spread = w_A × Price_A + w_B × Price_B (обычно w_A = 1 после нормализации)

**Реализация:** `statsmodels.tsa.vector_ar.vecm.coint_johansen()` — встроенный, быстрый, надёжный.

### 4.3 Fallback: Total Least Squares (TLS)

Если Johansen нестабилен (малый выборок или нон-стационарные остатки):
- `scipy.odr` с моделью линейной регрессии
- TLS учитывает ошибки в обоих переменных

### 4.4 Ребалансировка

- Частота: каждые RebalanceDays (дефолт 20) ИЛИ при падении corr < MinCorrelation
- Окно: последние LookbackWindow bars
- Если новый hedge ratio отличается от текущего > 10% → лог-алерт + обновление

## 5. ИСПОЛНЕНИЕ: ПАССИВНО-АГРЕССИВНАЯ МОДЕЛЬ

### 5.1 Принцип

**Дорогая нога → ЛИМИТКА (пассивная):** Фиксируем лучшую цену на BestBid/BestAsk  
**Дешёвая нога → МАРКЕТ (агрессивная):** Гарантируем исполнение

Это решает главную проблему арбитража — рассинхронизацию при двух лимитках.

### 5.2 Выбор ног

| Сценарий                     | Нога А (ЛИМИТКА)                         | Нога Б (МАРКЕТ)                       |
|------------------------------|------------------------------------------|---------------------------------------|
| Long Spread (Z > EntryZ)     | Short дорогой ноги на BestBid            | Long дешёвой ноги по рынку            |
| Short Spread (Z < -EntryZ)   | Long дешёвой ноги на BestAsk             | Short дорогой ноги по рынку           |
| Выход из Long Spread         | Long дешёвой ноги на BestAsk (close)     | Short дорогой ноги по рынку (close)    |
| Выход из Short Spread        | Short дорогой ноги на BestBid (close)    | Long дешёвой ноги по рынку (close)     |

### 5.3 Алгоритм (пошагово)

```
1. Сигнал: Z > EntryZ (Long Spread)
2. Определить: нога_A = дорогой инструмент, нога_B = дешёвый
3. Разместить LIMIT SELL нога_A @ BestBid, TIF=IOC, timeout=LegATimeoutSec
4. Ждать исполнения (poll каждые 100мс)
5a. ПОЛНЫЙ FILL → перейти к шагу 6
5b. ЧАСТИЧНЫЙ FILL ≥ MinFillRatio → корректировать объём ноги_B → шаг 6
5c. ЧАСТИЧНЫЙ FILL < MinFillRatio → ОТМЕНА остатка, сигнал отменён, лог
5d. ТАЙМАУТ → ОТМЕНА заявки, сигнал отменён, лог
6. Разместить MARKET BUY нога_B с объёмом = fill_qty × HedgeRatio
7. Верификация: обе ноги исполнены?
7a. ДА → позиция открыта, записать в state + trade log
7b. НЕТ (маркет не прошёл) → экстренное закрытие ноги_A по рынку, алерт
8. Проверить задержку: если T_B - T_A > MaxLegDelayMs → пометка «sync_violation»
```

### 5.4 Параметры исполнения

| Параметр              | Тип   | Дефолт | Диапазон       | Описание                                |
|-----------------------|-------|--------|----------------|-----------------------------------------|
| ExecutionMode         | enum  | PassiveActive | PassiveActive / Simultaneous | Режим исполнения           |
| LegATimeoutSec        | int   | 5      | 1 - 30         | Таймаут лимитки (сек)                    |
| LegBOrderType         | enum  | MARKET | MARKET / FOK   | Тип заявки для ноги Б                    |
| MinFillRatioLegA      | float | 0.50   | 0.3 - 1.0      | Мин. доля fill для перехода к ноге Б    |
| MaxLegDelayMs         | int   | 2000   | 500 - 5000     | Макс. задержка между ногами (мс)         |
| PriceOffsetBps       | int   | 0      | 0 - 10         | Смещение цены лимитки от Best (б.п.)    |
| UseIOC                | bool  | true   | true / false   | IOC для лимитки                          |
| AutoCancelOnTimeout   | bool  | true   | true / false   | Автоотмена при таймауте                  |
| EmergencyCloseLegA     | bool  | true   | true / false   | Экстренное закрытие ноги А при сбое Б    |
| MaxOrdersPerSec       | int   | 10     | 5 - 15         | Rate limit на заявки (Финам ~15 order/s) |

## 7. FAIR VALUE МОДЕЛЬ

### 7.1 Для фьючерсных пар (SiU6/SiM6, MIXU6/MIXM6)

```
FairSpread = Spot × (e^(r_diff × T/365) - 1) + DividendYield × T/365

где:
  r_diff = (ставка USD - ставка RUB) / 100  — разница ключевых ставок
  T       = дни до экспирации ближнего контракта
  DividendYield — релевантно только для индексных фьючерсов
```

Z-score считается от FairSpread:
```
Z = (ActualSpread - FairSpread - Mean) / Std
```

### 7.2 Для спот/фьючерс (SBER/SBRF)

```
FairBasis = Spot × (1 + r_cost × T/365 + DividendYield × T/365)
  r_cost  = ставка финансирования (~0.08 годовых)
```

### 7.3 Обновление

- **r_diff:** Обновляется при изменении ключевой ставки ЦБ (автоматически через MOEX ISS)
- **DividendYield:** Обновляется по дивидендному календарю (MOEX ISS API)
- **T:** Пересчитывается ежедневно

|---------------------|----------------------|------------------------------|
| MARKET (1 лот SI)   | 1-2 пт (0.001-0.003%)| OF-данные (стаканы + трейды) |

| LIMIT IOC (1 лот SI) | 0 пт                 | BestBid/BestAsk              |
| LIMIT IOC (>5 лотов) | 0-1 пт               | Частичный fill возможен      |

### 9.3 Полный RT для пары фьючерсов (SI)

```
Стоимость = 2 × 0.90₽ (вход: 2 ноги) + 2 × 0.90₽ (выход: 2 ноги) + Slippage
          = 3.60₽ + ~3₽ (маркет slippage)
          = ~6.60₽ на 1 RT

При средном профите ~35₽/RT → net ~28₽ → PF ~1.2-1.5
```

## 10. RATE LIMITER

### 10.1 Проблема
Финам ограничивает ~15 order/sec. При 10 парах с частичными филами, ретраями и экстренными закрытиями — можно упереться.

### 10.2 Решение: клиентский token bucket

```python
class RateLimiter:
    """Token bucket: MaxOrdersPerSec заявок в секунду."""
    def __init__(self, rate=10, burst=15):
        self.rate = rate    # tokens/sec
        self.burst = burst  # max tokens
    async def acquire(self):
        """Wait if bucket empty, then send."""
```

- **Rate:** 10 order/sec (дефолт), настраивается
- **Burst:** 15 (позволяет пакет до 15 за <1 сек, потом throttle)
- **При исчерпании:** Очередь FIFO с таймаутом 5 сек → алерт «rate_limited»

## 13. ЛОГИРОВАНИЕ

### 13.1 Формат

Structured JSON через Python `logging` → systemd journal (аналог OF-робота).  

**Категории:**

| Категория        | Содержание                                                | Пример                                      |

> **Почему не PostgreSQL/ELK:** Для одного Python-модуля — overkill. CSV+JSON покрывает все потребности. Если понадобится querying — DuckDB поверх CSV за 5 минут. ELK — когда будет 10+ роботов и нужна централизация.

## 17. СВОДКА ИЗМЕНЕНИЙ (v1.2 → v2.0)

| Изменение                                           | Причина                                     |
|-----------------------------------------------------|---------------------------------------------|
| Sharpe ≥ 2.0 → ≥ 1.0 (цель 1.3)                     | Нереально без HFT инфраструктуры            |
| DD ≤ 8% → < 15% (цель < 10%)                        | Реалистично для рыночного исполнения        |
| WR ≥ 65% → ≥ 55% (цель 60%)                         | Арбитраж: частые мелкие прибыли + редкие убытки |
| PostgreSQL/ELK → JSON + CSV + systemd journal       | Overkill для одного модуля                   |
| Добавлен Этап 0: Валидация пар (ADF + Johansen)     | Без доказательства edge — нет смысла писать код |
| Добавлен Этап 1: Бэктест до разработки              | Stop-loss на ТЗ: если нет alpha — не строим  |
| OLS → Johansen eigenvector для hedge ratio          | OLS даёт смещённый коэффициент               |
| MaxLegDelayMs: 500 → 2000                            | Финам latency не позволяет 500мс             |
| Добавлен Rate Limiter (token bucket)                | Финам ~15 order/sec, нужно контролировать    |
| Добавлен фильтр макро-событий (ЦБ, дивиденды)       | Сессии ЦБ — смерть для рублёвых пар          |
| Точные комиссии по инструментам                     | 0.018% — неверно для SI (реально 0.0012%)    |
| Убраны ROSN/SBER, добавлены с пометкой «валидация» | Разные сектора = нет коинтеграции              |
| Добавлена модель slippage на базе OF-данных         | У нас уже есть стаканы SiU6                  |
| Добавлена реконциляция (каждые 60 сек)             | Защита от рассинхрона стейта                  |
| StopLoss: % → рубли                                 | Рубли понятнее для контроля                  |
| Добавлен сессионный фильтр                          | Утренняя сессия = низкая ликвидность          |
