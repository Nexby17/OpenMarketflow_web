# RULES.md — Операционные правила OpenMarketflow

**Зачем этот файл.** Три реестра проекта отвечают на разные вопросы: `feature_list.json` — ЧТО изменено, `progress.md` — КОГДА и ПОЧЕМУ, `RULES.md` — КАКИЕ правила теперь действуют и ЧТО будет, если их нарушить. Правила рождаются из инцидентов; без отдельного файла они живут в чатах и головах и теряются (реестр фич уже однажды отстал на 20 позиций — с правилами повторять нельзя).

**Принцип:** правило ≠ фича. Правило — устойчивое ограничение или требование, действующее после того, как работа «сделана». Фича может устареть и быть заменена; правило остаётся, пока не явно отменено Дмитрием.

## Как читать и вести

- **Статусы:** `active` — действует как дисциплина/процесс; `code-guard` — закреплено кодом (ссылка на F-XXX); `proposed` — предложено по инциденту, ждёт решения Дмитрия; `deprecated` — отменено (не удалять — история).
- **Обеспечение:** каждое правило помечено, чем держится — `код`, `процесс` (дисциплина людей/агентов), `ручное`.
- **Жизненный цикл:** инцидент → карточка `proposed` → согласие Дмитрия → `active` → по возможности `code-guard`. Отмена правила — только Дмитрием, с датой и причиной.
- **Когда добавлять:** сразу после расследования инцидента (пока свежи доказательства). При дизайне новой фичи — сверяться с секцией своей области.
- **Формат:** индекс-таблица для быстрого скана + карточки с доказательствами. Идентификаторы R-XXX не переиспользуются.

## 1. Управление и разрешения

### R-001 — Старт/рестарт боевых роботов только Дмитрием
- **Статус:** active · **Обеспечение:** процесс · **Действует с:** 29.08 (решение Дмитрия)
- **Суть:** агент и код не поднимают live-процессы торговых роботов сами. Исключение — явное разрешение Дмитрия в чате, фиксируемое в progress.md.
- **Происхождение:** решение Дмитрия d55c515 «роботы — вручную»; подтверждено практикой (рестарты 29.09 и 30.09 — только по явному «перезапусти/запусти»).
- **Нарушение =** несанкционированная торговля реальными деньгами.

### R-002 — Торговая логика/параметры не меняются без решения Дмитрия
- **Статус:** active · **Обеспечение:** процесс · **Действует с:** 23.09 (расширено 30.09)
- **Суть:** фиксы тейка/фидов/журнала/инфраструктуры — можно; торговая логика, метрики, параметры и пороги ЛЮБОГО робота — только явное решение. Рабочая входная математика (dev_ann/zscore) не «улучшается» попутно.
- **Происхождение:** F-038 (29.09): «входы не трогаем, как договаривались»; 30.09 расширено правилом из AGENTS.md §4 при переносе в RULES.md.

## 2. Позиции и исполнение

### R-003 — Каждая смена режима логируется
- **Статус:** code-guard · **Код:** F-050 (main_arb/main_of/main_of_mx: log.warning на /start /stop /pause) · **С:** 30.09
- **Суть:** переход режима пишется с направлением (was → new) и размером позиции. «Робот сам включился/остановился» должно находиться в логе за секунды.

### R-004 — UI меняет режимы только через подтверждение
- **Статус:** code-guard · **Код:** F-050 (app.js: confirm() на Start/Pause/Stop/startViaServer) · **С:** 30.09
- **Суть:** фоновая вкладка не может молча включить торговлю. Подтверждение — на все действия, меняющие режим или позиции.
- **Происхождение:** 30.09 вкладка дважды самовключила OF Si; робот успел набрать 4 лота лонга за 12:00–13:25.

### R-005 — Журнал сделок = цены брокера
- **Статус:** code-guard · **Код:** F-048 (+F-013 для OF) · **С:** 29.09
- **Суть:** цена исполнения берётся у брокера (trade sub → REST GetTrades → gRPC avg). Оценка (лимитка/стакан) — только с меткой `estimate`/`mixed` в priceSource. Каждая запись несёт order_id всех ног.
- **Происхождение:** 29.09 журнал показал +644.19₽ при фактических −69.62₽ (расхождения leg B до 126 пт).

### R-006 — Исполнение ноги фиксируется сразу, даже при срыве второй
- **Статус:** active (принято Дмитрием 30.09) · **Обеспечение:** процесс; код-guard — F-051 (planned) · **Область:** arb orders/strategy
- **Суть:** если entry/exit второй ноги упал, а первая исполнилась у брокера — факт попадает в state/журнал немедленно; слой, которого нет у брокера (полностью или ногой), не считается «открытым». Включает отмену-с-проверкой: сорванная лимитка может исполниться после таймаута.
- **Происхождение:** 30.09 L14: leg A SELL 100 @97.43 исполнен брокером, робот записал leg_a_place_failed → голый шорт GZZ6 −1 без хеджа, обнаружено только сверкой.
- **Нарушение =** невидимая для робота позиция на реальные деньги.

### R-007 — Старт = сверка позиции с брокером
- **Статус:** code-guard · **Код:** startup-reconciliation (main_of/main_of_mx) · **С:** 29.08
- **Суть:** при старте позиция брокера сравнивается с state; расхождение → блокировка входов, mode=stopped, «investigate manually». DESYNC-монитор продолжает проверку в рантайме.
- **Происхождение:** порт PORT-B2; сработал корректно 30.09 ( поймал «broker 4 lots vs robot FLAT»).

### R-008 — Kill ≠ /stop
- **Статус:** active · **Обеспечение:** процесс · **С:** 30.09
- **Суть:** kill-процесса не трогает позиции и не шлёт ордеров (позиция восстанавливается из state при старте) — безопасен для рестартов. `/stop` закрывает позиции рыночными ордерами — применять осознанно: когда позицию нужно ОБЯЗАТЕЛЬНО закрыть; опасен при раскорреляции (пошлёт ордера в обе стороны от фантомного слоя).

### R-009 — Анти-дабл-клоз
- **Статус:** code-guard · **Код:** F-043 · **С:** 28.09
- **Суть:** close_all с ретраями защищён от повторного исполнения (фантомных позиций «в минус»).

## 3. Данные, журналы, сверки

### R-010 — Лента сделок брокера может быть неполной
- **Статус:** active · **Обеспечение:** процесс · **С:** 30.09
- **Суть:** GetTrades иногда отдаёт сделки с задержкой или не все (30.09: не было входов 19:00/19:23 OF, были «призраки» 19:34). Сверки журналов делать по позиции (GET /accounts/{id}) и за окно с запасом, не только по ленте.

### R-011 — Логи инстансов — раздельные файлы
- **Статус:** active (принято Дмитрием 30.09) · **Обеспечение:** код-guard — F-054 (planned; изначально бронировалось F-052, перенесено 30.09 — номер ушёл на фикс фантомного тейка) · **Область:** arb-инстансы (общий robot/logs/arb_YYYYMMDD.log)
- **Суть:** три арб-инстанса пишут в один файл — чужие события маскируют свои («LAYER #36» от BR-инстанса в логе GAZP), диагностика замедляется. Нужно: файл на инстанс (порт/пара в имени) + ротация.
- **Происхождение:** 30.09 расследование L14 — 20 минут ушло на фильтрацию чужих строк.

### R-012 — State живого процесса руками не редактировать
- **Статус:** active · **Обеспечение:** процесс · **С:** 29.09
- **Суть:** автосейв каждые 30 с перезатрёт внешние правки. Правки state — либо при остановленном процессе, либо через /reload-state (F-048).

## 4. Эксплуатация процессов и окружения

### R-013 — Старт процесса = env в той же команде; дефолтные state пустые
- **Статус:** active · **Обеспечение:** процесс + файлы · **С:** 30.09
- **Суть:** ARB_CONFIG_FILE/ARB_STATE_FILE задаются в той же exec-команде, что и Start-Process (env между командами теряется, параметр -Environment недоступен). Дефолтные state-файлы (arb_state.json и пр.) держать с layers=[] и mode=stopped — случайный старт без env не должен подхватывать мёртвые слои.
- **Происхождение:** 30.09 старт без env → фантомный L15 от 22.09 → daily_stop → EXIT ALL фантома → риск реальной лимитки SELL GAZP при нулевой позиции (отменена, ущерба нет).

### R-014 — «Cannot be canceled» = проверить статус ордера
- **Статус:** active · **Обеспечение:** процесс · **С:** 30.09
- **Суть:** отказ REST/GRPC отмены с «cannot be canceled» обычно значит «уже отменён/исполнен» — повторять отмену не нужно, нужно прочитать статус ордера и отреагировать на него. Терпимый cancel (tolerant) в коде — бэклог.

### R-015 — DP 5060 — критическая зависимость
- **Статус:** active (принято Дмитрием 30.09) · **Обеспечение:** код-guard — F-053 (planned: healthcheck + алерт) · **Область:** infra
- **Суть:** DataProvider лежит → фолбэки отмен/статусов мертвы (30.09: leg_a_place_failed + cancel failed одновременно). Нужно: healthcheck DP в main-циклах, алерт Дмитрию, и разбор почему DP не поднимается сам.
- **Происхождение:** 30.09 — тейк L14 сорвался именно потому, что gRPC упал, а DP-фолбэк лежал.

### R-016 — JWT/gRPC сбои ожидаемы
- **Статус:** active · **Обеспечение:** код (F-046 self-heal + ретраи) · **С:** 29.09
- **Суть:** UNAUTHENTICATED/TimeoutError — штатная среда Finam: любой сетевой вызов обязан иметь ретрай с бэкоффом и не ронять поток. F-046 не отменяет обработки отказов — сам F-046 иногда падает.

## 5. Проверки перед «готово»

### R-017 — «Готово» по позициям/журналу — только после сверки с брокером
- **Статус:** active · **Обеспечение:** процесс · **С:** 30.09
- **Суть:** закрытие/перезапись/ресинк считаются выполненными после подтверждения GET /accounts/{id} (позиции) и GetTrades (сделки), а не после записи в локальный state.

### R-018 — UI-фиксы проверяются в браузере
- **Статус:** active · **С:** 17.08
- **Суть:** любые правки веб-интерфейса принимаются только после реальной проверки: зайти на :5050, эмулировать действия пользователя (таймфреймы, вкладки, кнопки), приложить скриншот.

### R-019 — Коммит кода = три реестра тем же коммитом
- **Статус:** active · **С:** 23.09 (аудит edb22d0; 30.09 перенесено из AGENTS.md §7 целиком)
- **Суть:** каждый коммит кода/конфигов сопровождается записями в feature_list.json, progress.md, robot/PROGRESS.md. Без документации задача НЕ считается выполненной. Правила-инциденты — дополнительно в этот файл (RULES.md).
- **Детали процесса (перенесены из AGENTS.md §7):** коммит ссылается на F-XXX (`feat(F-XXX): ...` / `fix(F-XXX): ...`); нумерация F-XXX строго последовательная, перед присвоением проверять занятость (`git log --oneline --grep="F-0"` — дубль F-032 случился 22–23.09); восстановительные записи в реестр помечать note «восстановлено при аудите <дата>»; main-агент включает это правило в КАЖДЫЙ бриф код-агенту и проверяет выполнение до коммита.

### R-020 — Ротация боевых логов: хранить 30 дней
- **Статус:** active (принято Дмитрием 01.10) · **Обеспечение:** ручная чистка агентом при уборках + F-054 (раздельные логи) при реализации добавит авто-ротацию
- **Суть:** robot/logs/ — только актуальные журналы (30 дней); более старые удаляются без архива (сверки делаются по брокеру, R-010). Раздельные логи инстансов — F-054.
